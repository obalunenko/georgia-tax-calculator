# Bug Report: Bot accepts invalid and non-positive amounts

**Type**: Implementation drift (FR-011) and spec gap (no rule for amounts ≤ 0)
**Severity**: Medium
**Feature**: 002-currency-conversion (also affects 003-tax-calculation)
**Reported**: 2026-11-15
**Status**: Patched
**Patched**: 2026-11-15

## Description

The bot validates amounts with `parseMoneyAmount`
(`cmd/bot/handlers.go:697`), which uses `fmt.Sscanf("%f")`. Checked with Go
1.27.3:

| Input | Sscanf result | Error |
|-------|---------------|-------|
| `12abc` | 12 | none |
| `1,500` | 1 | none |
| `NaN` | NaN | none |
| `-Inf` | -Inf | none |
| `-5` | -5 | none |

The bot stores the raw text, so these inputs pass the amount step and fail
only after confirmation, in `service.Convert` (`moneyutils.Parse`), with
`can't convert … to decimal`. The CLI (`validateMoneyInput`,
`cmd/ge-tax-calc/prompts.go:369`) rejects them right away.

Neither interface nor the service rejects negative or zero amounts. Decision
of 2026-11-15 (002 tasks.md gap 2): income and conversion amounts MUST be
greater than 0; year income MUST be 0 or greater (0 is valid for the first
income of the year).

Secondary difference: the bot trims the input before validation, the CLI
does not (`validateMoneyInput` checks `TrimSpace` only for emptiness and
passes the raw value to `moneyutils.Parse`).

## Root Cause Analysis

The bot was added later (#221) with its own parser instead of reusing the
CLI rule; `cmd/ge-tax-calc` and `cmd/bot` are separate `main` packages, so
the CLI helper could not be shared, and no shared rule existed in
`internal/service`. The positivity rule was never specified.
