# Bug Report: Bot handlers can panic or race on a session

**Type**: Spec gap (no reliability requirement for handlers) and untested
flow
**Severity**: High (one panic stops the bot for every user)
**Feature**: 004-telegram-bot-platform
**Reported**: 2026-11-15
**Status**: Patched
**Patched**: 2026-11-15

## Description

Three related defects in `cmd/bot`:

1. **No panic recovery.** `registerHandlers` (`cmd/bot/bot.go`) registers no
   middleware. A panic in any handler terminates the process: in-progress
   flows of all users are lost and no maintenance message is sent. With
   `restart: unless-stopped` in Docker Compose, the restarted bot then sends
   the welcome-back broadcast to every known chat, so each crash notifies all
   users. The vendored telego provides `telegohandler.PanicRecovery()` and
   `PanicRecoveryHandler` (`vendor/github.com/mymmrac/telego/telegohandler/middleware.go:11`).
2. **Unchecked `msg.From`.** Command and text handlers read `msg.From.ID`
   without a nil check (`cmd/bot/handlers.go:25,47,70,84,109,129`);
   `trackUserMsg` checks it. Telegram documents `From` as possibly empty for
   messages sent to channels, so this is unlikely in private chats, but it
   becomes a crash once combined with item 1.
3. **Data race on session fields.** telegohandler runs each update in its
   own goroutine (`bot_handler.go:91`). `sessionStore` locks only the map
   (`cmd/bot/session.go`); handlers read and write `*session` fields
   (`flow`, steps, requests, `incomes` slice) without a lock. Two quick
   presses by one user can run two handlers on the same session at once:
   lost updates, a step applied twice, or a corrupted `incomes` slice. Not
   confirmed with `-race` because `cmd/bot` has no tests.

## Artifact Traceability

### spec.md (004)

- **Affected user stories**: US1 (run the bot), US2 (service commands).
- **Affected requirements**: FR-004 (handler registration), FR-008
  (per-user sessions in memory).
- **Gap identified**: no requirement that a failing handler must not stop the
  process, and none that updates of one user be handled one at a time. Edge
  Cases already state "one user can trigger concurrent handlers by pressing
  buttons quickly" without saying what must happen.

### plan.md

- Technical Decision 3 ("In-memory sessions keyed by user ID, guarded by a
  mutex on the map only; flows mutate the returned `*session` directly"):
  this decision causes item 3.
- Complexity Tracking, Concurrency row ("session fields not locked").
- Constitution Check VI (no tests in `cmd/bot`).

### tasks.md

- **Affected tasks**: T002 (`session`, `sessionStore`), T006 (`run`, handler
  registration), T007 and T008 (handlers).
- **False completions**: none; the code matches the migrated spec.
- **Missing tasks**:
  - register `telegohandler.PanicRecoveryHandler` that logs the panic with
    the chat ID and replies with a generic error;
  - skip messages with `msg.From == nil` (log at debug) in every message
    handler;
  - serialize updates per user: a mutex in `session`, held for the whole
    handler, including the service call;
  - tests: a session store test run with `-race` that drives two handlers on
    one user concurrently.

## Root Cause Analysis

The bot was written for one sequential dialogue per user; the concurrency
model of telegohandler (one goroutine per update) and failure isolation were
not part of the spec. Related: 004 tasks.md gaps 1, 2, and 5.

## Recommended Fix

1. Run `/speckit-bugfix-patch` to add requirements to 004 (handler failure
   isolation, per-user serialization), update plan decision 3, and add tasks.
2. Run `/speckit-bugfix-verify` to confirm consistency.
3. Implement panic recovery, nil checks, and the per-session lock with a
   `-race` test.
