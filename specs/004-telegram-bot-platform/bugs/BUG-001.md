# Bug Report: Stale inline buttons are applied to the current step

**Type**: Spec gap (no requirement to reject callbacks from old keyboards)
**Severity**: High (can silently produce a result for a wrong date)
**Feature**: 004-telegram-bot-platform (effects in 002-currency-conversion and
003-tax-calculation)
**Reported**: 2026-11-15
**Status**: Patched
**Patched**: 2026-11-15

## Description

Every inline button sends `cb:<value>` (`cmd/bot/keyboards.go`,
`buildInlineKeyboard`, `buildConfirmKeyboard`). `handleCallback`
(`cmd/bot/handlers.go`) strips the prefix and passes the value to the step
the session is in now, without checking which keyboard it came from. Old
messages keep their keyboards, so the user can press a button from any
earlier step or flow.

Effects:

| Step | Stale button | Result |
|------|--------------|--------|
| `calcStepConfirm` (`handlers.go:392`), `convertStepConfirm` (`:533`) | any value except `no` | the calculation or conversion starts |
| `calcStepAddMore` (`:364`) | any value except `yes` | the final review opens, the next income is skipped |
| `calcStepTaxType` | any value | `taxTypeFromItem` (`keyboards.go:84`) returns it unchanged; error only after confirmation |
| currency steps | a year or month | stored as a currency; error only after confirmation |
| `calcStepDay` for April | `31` from the March keyboard of the previous income | `time.Date` turns April 31 into May 1; tax is calculated at the May 1 rate **without an error** |
| `calcStepMonth` in the current year | a later month from a past-year keyboard | future date; result depends on what NBG returns for it |

The last two rows show that tagging callbacks with the step alone is not
enough: the old and the new keyboard belong to the same step.

Decision of 2026-11-15 (002 tasks.md gap 4): callback data carries the step
(`cb:<step>:<value>`), and data from another step is rejected.

## Artifact Traceability

### spec.md (004)

- **Affected user story**: US2 (service commands), scenario US2.5 ("a flow
  step that expects a button … text → ⚠️ Unexpected input"); there is no
  matching scenario for a button from another step.
- **Affected requirements**: FR-007 (routing to the active flow), FR-012
  (`cb:` prefix).
- **Gap identified**: no requirement that a callback be accepted only by the
  step and keyboard that produced it, or that its value be one of the
  options that step offers.

### spec.md (002, 003)

- 002 US3 (bot conversion), FR-009; Edge Cases ("Stale inline buttons …").
- 003 US3 (bot calculation), FR-010; Edge Cases ("Stale inline buttons …").

### plan.md

- 004 Technical Decision 2 (handler wrappers) and the routing description;
  needs a decision on the callback format and validation.
- 002 and 003 Project Structure (`keyboards.go`, `handlers.go`).

### tasks.md

- **Affected tasks**: 004 T004 (keyboards and `cb:` prefix), T008 (callback
  routing); 002 T015, T016; 003 T014, T015.
- **False completions**: none; the tasks match the spec, the spec is
  incomplete.
- **Missing tasks**:
  - encode flow and step in callback data, for example `cb:calc_day:31`,
    and keep it within Telegram's 64-byte `callback_data` limit;
  - in `handleCallback`, reject data whose step differs from the session
    step with `sendUnexpectedInput`;
  - check the value against the options the current step offers (years,
    months and days up to today for the selected year and month,
    `currencies.All()`, tax types, `yes`/`no`); this covers the same-step
    cases above;
  - make `taxTypeFromItem` return an error for unknown items;
  - table-driven tests for callback parsing and validation (possible
    without Telegram once the parsing is a plain function).

## Root Cause Analysis

The flows were designed as a linear dialogue where only the latest keyboard
is pressed. Telegram keeps old keyboards active, and the spec did not cover
that case.

## Recommended Fix

1. Run `/speckit-bugfix-patch` to update 004 (FR-007, FR-012, new
   requirement and scenario), 002 and 003 (Edge Cases, bot stories).
2. Run `/speckit-bugfix-verify` to confirm consistency.
3. Implement step-tagged callback data plus the value check. Alternative to
   consider during the patch: a per-prompt sequence number
   (`cb:<seq>:<value>`) rejects every old keyboard, including one from the
   same step, without per-step value lists.
